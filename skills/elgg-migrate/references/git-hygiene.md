# Git hygiene for plugin and site repos

Migrations generate a lot of local-only state: docker volumes, composer
caches, upgrade logs, Elgg data dirs, override files with host paths. None
of it belongs in git. This reference defines what belongs where and gives
ready-to-paste `.gitignore` patterns for plugin repos and Elgg site repos.

The rule that drives everything: **the repo is the source the migration
consumes, not the environment the migration runs in.** Anything generated
by the migration toolchain, the container, or the user's local workspace
is job state — keep it in `$XDG_STATE_HOME/elgg-migrate/`, never in the
plugin or site repo.

---

## What belongs in a plugin repo

Keep:

- `elgg-plugin.php`, `start.php` (legacy), `manifest.xml` (legacy)
- `composer.json` — do NOT commit `composer.lock` for a library-style plugin
- `classes/`, `views/`, `languages/`, `actions/`, `pages/`, `lib/`
- `src/` (modern PSR-4), `tests/` (PHPUnit + Playwright)
- `README.md`, `CHANGELOG.md`, `LICENSE`
- `.github/workflows/`, `phpunit.xml.dist`, `phpcs.xml.dist`, `playwright.config.ts`
- Upgrade scripts in `Elgg\Upgrade\Batch` classes

Never commit:

- `vendor/` — composer-managed, resolved per environment
- `node_modules/`, `package-lock.json` unless the plugin ships JS tooling
  (if it does, lock it; otherwise treat JS the same as PHP deps)
- Any file generated during migration in `$XDG_STATE_HOME/elgg-migrate/`
- IDE state: `.idea/`, `.vscode/`, `.phpunit.result.cache`, `.phpcs-cache`
- OS junk: `.DS_Store`, `Thumbs.db`
- Build artifacts: `dist/`, `build/`, `*.log`, `coverage/`, `.phpunit.cache/`
- Local tool state from this skill: any file matching `.elgg-migrate*`,
  `deps.lock.json`, `em-*` (container/project names)

### Plugin `.gitignore` (paste-ready)

```gitignore
# composer
/vendor/
composer.lock

# node
/node_modules/
/dist/
/build/
npm-debug.log*
yarn-debug.log*

# tests
/.phpunit.result.cache
/.phpunit.cache/
/coverage/
/test-results/
/playwright-report/
/blob-report/
/.playwright/

# linters
/.phpcs-cache

# but blocklisted defensively in case the orchestrator is misconfigured)

```

## What belongs in an Elgg site repo

An Elgg site repo owns the *composition*: which plugins, in which order,
with which settings. It does not own the plugin source itself, nor the
runtime environment.

Keep:

- `composer.json` + `composer.lock` — pins the exact site composition
- `mod/` — ONLY the site-specific custom plugins; upstream plugins are
  installed via composer into `mod/` and must be gitignored
- `elgg-config/settings.php` template (no secrets), `.htaccess` customizations
- Dockerfile / compose template if the site ships its own infra
- `engine/settings.example.php` if you maintain a customized example
- Deployment manifests: `k8s/`, `ansible/`, `fly.toml`, etc.

Never commit:

- `vendor/` — composer-managed
- Upstream composer-installed plugins in `mod/` (hype*, elgg/*, coldtrick/*)
  — these belong to composer, not git
- `dataroot/` or any `data/` directory — user uploads, caches, sessions
- `engine/settings.php` if it contains real credentials — ship
  `settings.example.php` and have deploys copy it
- `.htaccess` if it was auto-generated by Elgg installer (keep only your
  customizations; commit those as a patch or in a separate file)
- Simplecache / system cache output: `cache/`, `views_simplecache/`
- Session files, log files, upload dirs
- Docker override files with absolute host paths — those are a local-dev
  concern, not a repo concern
- Skill / tooling state: `$XDG_STATE_HOME/elgg-migrate/` is outside the
  repo by design; if you ever see an `elgg-migrate/jobs/` dir appear
  inside the site repo, the orchestrator is misconfigured — stop and fix
  it before committing

### Elgg site `.gitignore` (paste-ready)

```gitignore
# composer
/vendor/

# upstream plugins come from composer, not git
/mod/*
# ...but keep the custom, site-owned plugins:
!/mod/bodyology_*
!/mod/<your-site-prefix>_*
!/mod/.gitkeep

# runtime data (NEVER commit)
/dataroot/
/data/
/engine/settings.php
/.htaccess.local
/cache/
/views_simplecache/
/storage/

# logs
*.log
/logs/

# docker local state
docker-compose.override.yml
.env
.env.local

# ide / os
/.idea/
/.vscode/
.DS_Store
Thumbs.db

# elgg-migrate job state — must never land in a site repo
.elgg-migrate*
/elgg-migrate/
```

Note the `mod/` pattern: blocklist everything, then allowlist the plugins
the site actually owns. That guarantees composer-installed plugins stay
out of history even if someone runs `git add mod/`.

## Migration-specific pitfalls

These are the failure modes that put junk in git during a migration.
The skill's orchestrator avoids them by design, but the agent should
verify before every commit:

1. **Override files with host paths.** The old workflow hand-edited
   `docker/elgg4/docker-compose.override.yml` with absolute paths like
   `/home/<user>/Data/...`. Those files must never be committed. The
   new orchestrator writes overrides under
   `$XDG_STATE_HOME/elgg-migrate/jobs/<job>/override.yml` — outside
   any repo.
2. **`vendor/` after a local `composer install`.** Migration often
   requires `composer install` inside the plugin to run PHPUnit. The
   resulting `vendor/` must not be committed. Always check `git status`
   before `git add .` and prefer `git add <specific-files>`.
3. **PHPUnit / Playwright caches.** `.phpunit.result.cache`,
   `playwright-report/`, `test-results/` — all local, all gitignored.
4. **Composer-installed plugins inside a site's `mod/`.** If `mod/hype*`
   shows up as untracked in a site repo, the `.gitignore` is wrong —
   see the blocklist-then-allowlist pattern above.
5. **Data and cache dirs.** `dataroot/`, `views_simplecache/`, `cache/`
   can grow to gigabytes and contain user PII. Never commit.
6. **Editor / IDE state.** `.idea/`, `.vscode/`, `*.swp`, `*.bak` — use
   a global gitignore (`git config --global core.excludesfile`) so these
   never sneak in per-repo.
7. **Skill artifacts.** Nothing from `skills/elgg-migrate/` or
   `$XDG_STATE_HOME/elgg-migrate/` ever belongs in a plugin or site
   repo. If a `jobs/` dir appears inside the plugin you're migrating,
   the orchestrator wrote to the wrong place — file a bug, don't commit
   around it.

## Pre-commit check (agent should run this before every commit)

```bash
# Confirm nothing forbidden is staged
git diff --cached --name-only | grep -E \
  '(^|/)(vendor|node_modules|dataroot|data|cache|\.idea|\.vscode|coverage|\.phpunit\.result\.cache|playwright-report|test-results)(/|$)|\.env$|settings\.php$|docker-compose\.override\.yml$' \
  && { echo "forbidden path staged — aborting"; exit 1; } || true
```

If that grep matches, stop and fix `.gitignore` before retrying the commit.
