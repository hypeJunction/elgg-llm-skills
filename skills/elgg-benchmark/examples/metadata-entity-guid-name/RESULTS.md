# Results — `metadata (entity_guid, name)` composite index

Generated by `./run.sh` against clean, throwaway containers (tmpfs datadir,
`--innodb-buffer-pool-size=1G`), 1,000,000 deterministic metadata rows
(50,000 entities × 20 rows), workload = 10,000 `getIDsByName` lookups
(`WHERE entity_guid = ? AND name = ?`).

The headline metric is `Handler_read_next` — rows the storage engine walked,
cache-independent and identical run-to-run. Wall-clock is secondary (warm buffer
pool, median of three runs).

## Headline: rows examined for 10,000 lookups

| Engine | `Handler_read_next` BEFORE | AFTER | EXPLAIN key BEFORE → AFTER | rows/scan BEFORE → AFTER |
| --- | ---: | ---: | --- | --- |
| mysql:8.0 (8.0.46) | 130,003 | **0** | `entity_guid` → `entity_guid_name` | 20 → 1 |
| mysql:8.4 (8.4.10) | 130,003 | **0** | `entity_guid` → `entity_guid_name` | 20 → 1 |
| mariadb:10.6 (10.6.27) | 130,003 | **0** | `entity_guid` → `entity_guid_name` | 20 → 1 |
| mariadb:10.11 (10.11.18) | 130,003 | **0** | `entity_guid` → `entity_guid_name` | 20 → 1 |

Every engine agrees: before the index each lookup resolves `entity_guid` and then
walks ~13 sibling rows on average to filter `name` (130,003 rows across 10k
lookups); after the index each lookup is a direct composite seek that touches
**zero** extra rows (`Handler_read_next = 0`). `EXPLAIN` confirms the optimizer
switches from the single-column `entity_guid` index (estimating 20 candidate rows,
~6% passing the `name` filter) to `entity_guid_name` (1 row, 100% filtered).

## Wall-clock (median of 3 × 10,000 lookups, warm buffer pool)

| Engine | BEFORE | AFTER |
| --- | ---: | ---: |
| mysql:8.0 | 0.42s | 0.37s |
| mysql:8.4 | 0.41s | 0.32s |
| mariadb:10.6 | 0.42s | 0.30s |
| mariadb:10.11 | 0.40s | 0.30s |

Wall-clock improves modestly here because the whole dataset is memory-resident and
each lookup is dominated by round-trip overhead inside the stored-procedure loop —
so the eliminated row-walk shows up far more sharply in the deterministic
`Handler_read_next` counter than in wall time. On a real install where metadata
does not fit entirely in the buffer pool, the eliminated per-lookup scan also
removes page reads, so the wall-clock gap widens.

## Interpretation

- The `metadata` hot path (`getIDsByName`, the metadata preloader, and
  `elgg_get_entities()` with `metadata_name_value_pairs`) reads by
  `(entity_guid, name)`. This index makes that a single index seek.
- Impact scales with how many metadata rows each entity carries — and that count
  grew when `private_settings` was merged into `metadata`
  (migration `20220825064811`).
- This brings `metadata` in line with `annotations`, which has carried the
  equivalent `entity_guid_name` index since 2020 (`20200331083912`).
